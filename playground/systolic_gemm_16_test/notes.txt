One thing to flag before the results: you asked for the "golden CPU top using our Allo code." I couldn't literally do that — allo.exp.build needs this fork's own from-source LLVM/MLIR build (allo/_mlir), which isn't set up on this machine, and even upstream, allo.grid_map/allo.stream_global have no CPU lowering at all yet (that's explicit in mesh/TODO and in playground/README.md's own note: "grid_map in CPU simulator — upstream Allo; until then use systolic_cpu.py as golden"). So I followed that same established fallback: golden.py is a direct Python transcription of systolic.py's pe() — same branches, same put/get call sites, same accumulation order — run as cooperative generators over FIFO queues standing in for Stream<T,DEPTH>, not an Allo-executed simulation.

What ran:
- A, B: fixed-seed (1234), signed, non-integer, range ±6 — not a degenerate all-ones/zeros case.
- The PE-dataflow golden converged in 5 rounds and matched numpy's A @ B to float32 precision (max diff ~1e-6), confirming the design's control flow really does compute a correct GEMM.
- test_data.h now has the literal A, B, and the golden C baked in as float32 constants.

What's staged for the CUDA machine: test_harness.cu allocates device buffers, copies test_A/test_B over, calls the generated systolic_gemm_16(...) host wrapper, copies C back, and diffs every element against test_C_expected with a tight tolerance (float32 accumulation order should match almost exactly, not just GEMM-tolerance-close). Build later with:
cd playground/systolic_gemm_16_test
nvcc -O3 -arch=sm_80 test_harness.cu -o test_harness && ./test_harness

Note: I hit one real bug writing the simulator worth mentioning — my first deadlock-detector compared FIFO occupancy between rounds, but this design's row-major PE traversal happens to align with its dependency direction, so a queue fills and fully drains within a single pass and reads back as "0 items, no change" even mid-computation, so I had to switch to counting actual put/get operations instead.
